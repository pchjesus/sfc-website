## 현황 및 원칙
기존 Studio 계정 관리에서 Auth에 이미 존재하는 이메일을 cms_admins allowlist에 추가하고, 다른 관리자의 운영 권한을 해제할 수 있다. 계정 삭제가 아니라 권한 해제다. SQL guard는 최대 3명, 본인 직접 해제 금지, 마지막 관리자 해제 금지를 적용한다. Auth 사용자 생성·초대·비밀번호 재설정·계정 자체 삭제는 별개이고 실제 검증은 미실행. 현재 SQL guard의 이메일 조회는 존재 여부를 확인하지만 email_confirmed_at 조건은 명시하지 않으므로 활성화 전 검증 필요. cms_posts.author_id는 Auth 사용자 삭제를 restrict하므로 게시물·이력 보존 없이 계정을 강제 삭제하지 않는다.

## A0 — P4 완료 후 첫 관리자
- 소유자가 사용할 실제 이메일 확정 및 명시적 계정 생성 승인. 비밀번호/토큰을 채팅·GitHub·로그에 남기지 않음.
- 기존 README 절차로 승인된 Supabase Auth 초대/계정 활성화 및 최초 allowlist 등록. 공개 가입 비활성화 및 복구 redirect 확인. 실제 환경/권한 확인 후에만 운영 사용.
- 소유자가 직접 비밀번호 설정/로그인; Studio, 로그아웃, 비밀번호 복구, 권한 없는 세션 및 파일 정책은 승인된 테스트 범위에서 검증. 실제 운영 콘텐츠 없음.

## A1 — 계정 관리 편의성
- 기존 계정 목록/최대 3인 체계 유지. 계정 활성·초대 대기·권한 해제 상태, 현재 사용자 및 인원 표시. 기존 추가/해제 API의 실제 affected row 검증과 오류/동시 요청/재조회 보호.
- 관리자 초대는 신뢰된 서버 기능(예: Supabase Edge Function)에서 현재 관리자 권한 재검증 후 Auth 관리자 API 호출; 브라우저 publishable key로 Auth admin API 호출하지 않는다. 서버 비밀키/메일 개인정보 보호. 실제 생성/메일 발송/DB 변경은 별도 승인. 초대 중복·만료·실패/취소 및 인원 상한을 처리하고, 초대 완료 전에는 활성 운영 권한을 부여하지 않는다.
- 졸업 시 신규 관리자의 계정을 확인하고 권한 인수 → 새 관리자의 정상 로그인/업무 확인 → 기존 관리자의 cms_admins 권한 해제 → 다음 API 요청 차단 검증. 3명 모두 활동 중이면 기존 한 명을 다른 현직 관리자가 해제하여 자리를 확보한 뒤 초대; 최소 한 명 유지. 마지막 관리자 또는 본인 직접 삭제 금지.
- 권한 해제가 기본값. Auth 계정 삭제는 별도 고위험 작업이며 기록 보존/참조/FK·세션 폐기 정책 검토 후 명시 승인. 과거 보고서와 작성자 표기·revision·운영 이력을 삭제하지 않음. 다른 운영자에게 비밀번호를 전달하는 대신 각자 계정 사용.
- 기록: 누가 누구를 언제 초대/승인/해제했는지 비공개 운영 로그, 개인정보 최소화. 공개 People 프로필과 Studio 계정을 별개로 관리.

## A2 — 검수
1. anon/비관리자 초대·추가·해제 차단(직접 API 포함).
2. 1→2→3명 등록과 4번째/동시 등록 거부, 중복 이메일/미확인 이메일/만료 처리.
3. 관리자 교체 후 기존 세션의 쓰기 거부, 새 관리자 로그인 성공.
4. 마지막 관리자 보호, 본인 해제 방지, 실패/취소 시 현재 권한 유지.
5. 권한 해제 뒤 기존 글/연구/이력 보존 및 복구 가능 여부.
6. 실제 계정 삭제는 별도 검증·명시 승인 전 UI로 제공하지 않음.
7. 실제 테스트는 staging 우선, 운영 계정은 소유자 승인 후 제한된 범위. mock 성공을 실환경 검증으로 표시 금지.

P0/P1에서 Auth 관리자 API·실제 계정·운영 DB는 변경하지 않는다. A0는 P4 이후, A1/A2는 별도 검수 작업으로 진행한다. 기존 권한 추가/해제는 존재하나 실제 신규 Auth 초대/영구 삭제 UI는 아직 구현되지 않음.
